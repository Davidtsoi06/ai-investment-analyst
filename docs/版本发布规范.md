## 一、版本号规则

- 语义化版本 SemVer：主版本.次版本.修补（v1.2.3）。
- 阶段版本节奏：S0→v0.1.0，P0→v0.2.0，P1→v0.3.0，P2→v0.4.0，P3→v0.5.0，P4→v0.6.0，P5→v1.0.0。
- 修复类变更升 patch，功能类升 minor，破坏性变更升 major。

## 二、发布前检查清单（缺一不可）

1. 功能完成并通过该步骤/阶段验收标准（见开发执行计划）。
2. 开发日志已更新（当日完成/待办）。
3. README.md 已更新：新增/变更的功能说明、界面截图（如适用）、版本徽章、免责声明。
4. CHANGELOG.md 已更新：新版本条目（Added/Changed/Fixed，参考理财软件 CHANGELOG.txt 风格）。
5. 版本号已 bump（package.json / electron-builder 配置 / 后端版本文件）。
6. RELEASE_NOTES.md 已更新（发布说明，供 GitHub Release 使用）。
7. **用户确认**：已向用户汇报变更清单并获得明确确认（记录于开发日志）。

## 三、打包流程（本地）

1. 构建前端（npm run build）。
2. 打包后端：PyInstaller 生成单文件 exe。
3. electron-builder 生成 NSIS 安装包。
4. **清理旧安装包**：构建前删除 dist/release 目录中的旧版安装包与旧产物，确保发布目录只保留当前版本。

## 四、旧安装包清理规则（重要，防止占用存储空间）

1. 本地：每次打包前清空构建输出目录，仅保留当前版本安装包；data/backup 不受影响。
2. GitHub Releases：发布新版本后，删除旧版本 Release 中的安装包资产（使用 gh release delete-asset 或 GitHub 网页删除）；Release 记录与 tag 保留（便于回溯变更），仅清理二进制资产。
3. 定期检查：发布后确认远端仅当前版本资产存在。

## 五、推送与发布流程（标准顺序）

0. **用户确认（强制，不可跳过）**：版本内容完成后，先向用户汇报变更清单与发布计划（版本号、README/CHANGELOG 更新点、安装包变更），**必须经用户明确确认后才允许推送**，严禁直接推送。确认结果记录于当日开发日志。
1. git add 全部变更 → git commit（约定式提交，如 feat: 完成 XX 功能）
2. 更新 README.md / CHANGELOG.md / RELEASE_NOTES.md（见第二节检查清单）
3. git tag vX.Y.Z
4. git push origin main --tags（**仅限已获得用户确认后执行**）
5. GitHub Actions 自动构建安装包并发布 GitHub Release（release notes 取 RELEASE_NOTES.md）
6. 发布完成后：删除旧版本 Release 安装包资产（见第四节）
7. 应用内 electron-updater 提示用户更新（后续版本生效）

## 六、CI/CD（.github/workflows）

- ci.yml：push 触发 → 安装 Node/Python 依赖 → 前端构建 → 后端 PyInstaller 打包 → 单元测试 → electron-builder 打包。
- release.yml（或 ci 内按 tag 分支）：打 tag 时创建 GitHub Release 并上传安装包。
- 参考：理财软件 .github/workflows/ci.yml + electron-builder.yml 实践，直接复用改造。

## 七、发布后动作

1. 更新当日开发日志（发布版本号、变更摘要、遗留问题）。
2. 向用户汇报发布结果（版本号、Release 链接、安装包路径）。
